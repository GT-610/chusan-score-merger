# 中二节奏 分数合并器

把「落雪咖啡屋」导出的成绩列表合并进 RinNet 的存档文件。

**整个过程在浏览器本地完成，文件不上传、不经过任何服务器。**

---

## 快速开始

```bash
bun install
bun run dev          # 开发服务器
bun test             # 运行测试
bun run typecheck    # 类型检查
bun run build        # 产出 dist/
```

产物是纯静态文件，`bun run build` 后用任意静态服务器托管 `dist/` 即可。

## 使用方法

1. 在 RinNet 导出 JSON 存档。
2. 在「落雪咖啡屋」导出 CSV 成绩列表。
3. 打开页面，分别选择这两个文件，点击「开始合并」。
4. 查看报告，确认无误后下载 `{原名}_merged.json`。
5. 把新文件导入 RinNet。**原始存档不会被覆盖。**

## 合并规则

合并的核心是**单调性**：任何维度都不会被降低。

| 字段 | 规则 |
|---|---|
| `scoreMax` | 取最高分 |
| `scoreRank` | **由 `scoreMax` 推出**，不采信 CSV 的 `rank` 列 |
| `isSuccess`（灯号） | 取较高灯号 |
| `isFullCombo` | 任一来源存在 FC 即为 FC |
| `isAllJustice` | 任一来源存在 AJ 即为 AJ（并强制 FC） |
| `fullChain` | 取较高等级 |

几条容易误解的点：

- **是否通关不影响合并。** 分数更高的未通关成绩同样会被写入，因为分数与
  灯号是两个独立维度。
- **游玩次数（`playCount`）不会被修改。** 工具无从得知真实的游玩次数，
  编造一个数字是对玩家游玩历史的误报。原脚本会为每条更新记录 +1，本工具
  刻意不这样做。
- **`missCount` 恒有值**（未 FC 时为 `0`）。服务器把这些字段建模为非空整数，
  缺失字段比写 `0` 更危险。

### 关于评价等级

评价等级是分数的**严格函数**，14 个区间互不重叠：

| 评价 | 分数区间 | | 评价 | 分数区间 |
|---|---|---|---|---|
| D | 0 – 499,999 | | SS | 1,000,000 – 1,004,999 |
| C | 500,000 – 599,999 | | SS+ | 1,005,000 – 1,007,499 |
| B | 600,000 – 699,999 | | SSS | 1,007,500 – 1,008,999 |
| BB | 700,000 – 799,999 | | SSS+ | 1,009,000 – 1,010,000 |
| BBB | 800,000 – 899,999 | | | |
| A | 900,000 – 924,999 | | | |
| AA | 925,000 – 949,999 | | | |
| AAA | 950,000 – 974,999 | | | |
| S | 975,000 – 989,999 | | | |
| S+ | 990,000 – 999,999 | | | |

CSV 的 `rank` 列只用于**交叉校验**：一旦与分数推出的结果不符，会在
「提示」标签页中列出。旧版本（PARADISE LOST 及以前）阈值不同，只有 11 级，
这类分数会被单独标记。

### 关于游玩记录

补写「最近游玩记录」是默认开启的选项，但有两条硬性限制：

- **只在 CSV 该条成绩带有 `play_time` 时写入。** 不用 `upload_time` 兜底 ——
  一次上传往往包含很多首曲目，上传时间不能代表游玩时刻。缺时间的记录会被
  跳过并在「未写日志」标签页中列出。
- **ULTIMA 不写入。** 服务端的最近游玩查询会排除该难度，写了也不会显示。

`sortNumber` 是**场次 ID 而非时间戳**（同一局三首共享一个值），注入时会在现有
最大值之上逐条递增。`playDate` 取当日零点，`userPlayDate` 为实际游玩时刻，
均为不带时区的 UTC+9 墙钟时间。

### CSV 解析

这些导出文件的曲名中**含有逗号和转义引号**：

```
2031,"Little ""Sister"" Bitch",13+,3,643590,...
2461,"《創造》 ～ Cries, beyond The End",13+,2,1004946,...
```

按逗号切分会静默错行，因此解析器是完整的 RFC 4180 实现。

难度**只取 `level_index`**（谱面内部 ID），不参考人类可读的 `level` 文本 ——
两者并不等价，因为谱面会随版本重新定级。在真实存档上比对时，有 16 首曲目
出现了直接矛盾（CSV 说 index 2 / "10"，存档里却是 level 3）。

## 未知枚举值的处理

沿用原脚本的行为：未知值**降级为 0**（未通关）并继续执行，而不是中断合并。
区别在于**每次降级都会被记录下来**，在「提示」标签页中连同曲目与原始值
一并列出。静默降级是原脚本最危险的地方 —— 缺失的那条信息永远不会有人发现。

灯号表包含全部 7 档，其中 `absolutep` = 5（ABSOLUTE+）是 LUMINOUS 时代被 VERSE
撤销的档位。保留它是为了让残留的旧数据不至于掉进 0；删掉它反而会造成降级。

## 部署到 Cloudflare Workers

`wrangler.jsonc` 采用**纯静态资源**配置，不含 Worker 脚本。

这是必要的：3.4 MB 存档的解析与重新序列化约需 18–40 ms（JavaScriptCore 与
V8 实测），而免费版 Workers 每次请求的 CPU 上限只有 10 ms，稳态必然触发
Error 1102。把合并放在客户端同时还带来隐私收益——成绩数据根本不离开设备。

无 Worker 脚本时，静态资源由边缘直接吐出，不进入 isolate，Cloudflare 明确
标注此类请求**免费且不限量**。

```bash
bun run build
npx wrangler deploy     # 需要先登录 Cloudflare
```

注意不要开启 `run_worker_first`：免费套餐一旦超配额，它会返回 429 而不是回退
到静态资源，页面会直接不可用。

## 项目结构

```
src/
  core/
    types.ts      ALLNET 实体字段的类型定义
    constants.ts  阈值表、灯号表、FULL CHAIN 表
    csv.ts        RFC 4180 解析器
    merge.ts      合并内核（纯函数，无 IO，可直接单测）
  worker/
    protocol.ts   页面与 Worker 之间的消息契约
    merge.worker.ts  Worker 入口
  ui/             页面与样式
test/
  core.test.ts       解析器与阈值表
  merge.test.ts      合并规则
  reference.test.ts  与原脚本的等价性
  output.test.ts     下载产物的字节级校验
```

合并内核是纯函数，不碰 IO、时钟和随机数，因此所有行为都可以直接单测。

## 等价性验证

`test/reference.test.ts` 用同一对真实文件固定住了与原脚本的等价性：必须得到
**新增 25 条、更新 37 条**。这两个数字来自对原 Python 脚本的实际运行。

浏览器中实测同样得到 25 / 37 / 0 条提示。
